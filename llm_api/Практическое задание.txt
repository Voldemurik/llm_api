Практическое задание по программному взаимодействию с большими языковыми моделями (LLM), обработке структурированных данных и разработке надёжных AI-приложений.

Вам предстоит получить персональный вариант задания, реализовать Python-приложение для работы с GigaChat API, научиться проверять входные данные и ответы модели, защищаться от prompt injection и анализировать расход токенов.

В отличие от обычного общения с чат-ботом, здесь модель становится частью программного конвейера. Важно не просто получить ответ, а обеспечить его корректный формат, обработку ошибок и возможность автоматической проверки.

Для выполнения используется GigaChat API. Вы сможете выбрать доступную модель, но сам провайдер фиксирован, чтобы обеспечить единые условия выполнения и проверки задания.

Вам предстоит обработать 10 персональных тестовых случаев, включая обычные запросы, сложные ситуации, некорректные входные данные и попытки prompt injection.

Работа выполняется индивидуально в GitVerse с использованием Git, Python, API и CI/CD. Итоговая проверка запускается вручную и выполняет реальные запросы к GigaChat.

Использование LLM является обязательной частью задания, однако корректность входных данных, формат результата и обработка ошибок остаются ответственностью вашей программы.

Подробная инструкция — после нажатия на «Добавить ответ на задание».

Контрольное задание
Ссылка на задание
GitVerse Lab: перейдите по ссылке-приглашению.

Перейдите в репозиторий практики и внимательно изучите START.md.

Что нужно сделать
Создайте собственную рабочую ветку в GitVerse.

Дождитесь завершения автоматической генерации персонального варианта в CI/CD.

Изучите появившиеся TASK.md, assignment.json и тестовые случаи в cases/.

Ознакомьтесь с TASK_CONTRACTS.md, где описан ожидаемый формат результатов.

Каждый студент получает индивидуальный набор из 10 случаев по одному из восьми направлений: классификация обращений, аудит поставок, проверка свидетельств, извлечение сроков, извлечение сущностей, проверка правил, анализ инцидентов или маршрутизация запросов.

Главная задача — создать программу, которая не просто обращается к LLM, а контролирует весь процесс обработки данных.

Часть 1. Подготовка API
Изучите основы HTTP API: запросы, ответы, заголовки, авторизацию и формат JSON.

Настройте доступ к GigaChat API согласно START.md.

Авторизационные данные должны передаваться через переменную окружения GIGACHAT_CREDENTIALS или защищённые секреты GitVerse.

Запрещено сохранять ключи, токены и другие секреты в репозитории.

Выберите доступную модель GigaChat и укажите её в model_config.json.

Выбор модели необходимо объяснить в итоговом README.md.

Часть 2. Реализация Python-приложения
Откройте src/app.py и реализуйте пять предусмотренных функций.

Функция	Назначение
validate_input()	Проверка входного JSON, обязательных полей, типов и ограничений
build_prompt()	Формирование инструкций для модели с учётом требований задачи
parse_response()	Извлечение и проверка структурированного ответа модели
extract_usage()	Получение фактической статистики токенов из ответа API
build_run_report()	Формирование сводного отчёта о выполнении тестов
Реализуйте проверку входных данных до обращения к API.

Некорректный JSON, неправильные типы и другие нарушения входного контракта должны обрабатываться программой самостоятельно.

Не следует отправлять заведомо некорректные данные модели и расходовать на них токены.

Разработайте промпт для своего направления.

Он должен объяснять модели предметную задачу, требуемые поля ответа и ограничения.

Особое внимание уделите prompt injection: инструкции, содержащиеся внутри пользовательских данных, не должны изменять правила работы программы.

Реализуйте обработку ответа модели.

Необходимо получить JSON, проверить его структуру и убедиться, что результат соответствует контракту из TASK_CONTRACTS.md.

Синтаксически корректный JSON ещё не гарантирует правильного результата.

Часть 3. Тестирование и статистика
Проверьте программу локально на персональных случаях из cases/.

Убедитесь, что некорректные входные данные отклоняются без обращения к GigaChat.

Проверьте обработку сложных случаев и попыток prompt injection.

Реализуйте сбор статистики токенов из реальных ответов API.

Необходимо учитывать количество запросов, успешность проверок и расход входных и выходных токенов.

Запрещено подставлять заранее придуманные ответы модели или вымышленные значения статистики.

Часть 4. Документация и боевой запуск
Заполните README.md.

Опишите реализованное решение, выбранную модель, особенности валидации, защиту от prompt injection, обработку ответов и сбор статистики.

Проверьте, что в репозитории отсутствуют секреты и временные файлы с авторизационными данными.

Сохраните изменения в своей рабочей ветке.

Запустите итоговый workflow в разделе CI/CD вручную.

Боевой запуск выполняет новые реальные запросы к GigaChat, а не просто проверяет ранее сохранённые результаты.

По результатам работы формируются:

results/ — результаты обработки персональных случаев;
run_report.json — сводная статистика запуска.
Ожидается обработка 10 случаев, из которых два некорректных должны быть отклонены локально, а восемь остальных — обработаны через GigaChat API.

Изучите отчёт CI/CD. При необходимости исправьте ошибки и повторите проверку.

Не запускайте боевую проверку без необходимости: каждый запуск обращается к внешнему API.

После успешного выполнения создайте Pull Request из рабочей ветки в master.

Важно
Использование GigaChat API обязательно.
Нельзя заменять реальные вызовы API заранее подготовленными ответами.
Некорректные входные данные должны отклоняться до обращения к модели.
Ответы модели необходимо проверять на соответствие JSON-контракту.
Prompt injection необходимо учитывать при формировании инструкций.
Секреты запрещено сохранять в репозитории.
README.md должен содержать описание собственной реализации, а не незаполненный шаблон.
Успешный CI/CD подтверждает выполнение технических требований, но не гарантирует максимальную оценку. Содержательную корректность результатов дополнительно оценивает преподаватель.

Критерии оценки
Максимальная оценка — 5 баллов.

0 баллов — студент не приступил к выполнению задания.

0,5 балла — работа начата, но обязательные технические проверки не пройдены. Приложение не реализовано полностью, отсутствуют необходимые результаты или не выполнены требования к формату.

2,5 балла — приложение реализовано, выполняет реальные запросы к GigaChat, формирует необходимые артефакты и проходит основные технические проверки, однако часть результатов некорректна, имеются недостатки в обработке сложных случаев, защите от prompt injection или документации.

5 баллов — приложение корректно обрабатывает персональные случаи, соблюдает контракты входных и выходных данных, устойчиво к предусмотренным попыткам prompt injection, формирует достоверную статистику токенов и успешно проходит техническую проверку.

При содержательной оценке преподаватель учитывает долю корректно обработанных персональных случаев.

Для завершённой работы базовая оценка определяется качеством выполнения технических требований, а итоговый балл рассчитывается пропорционально числу корректных результатов:

Итоговый балл = базовая оценка × количество корректных случаев / 10
