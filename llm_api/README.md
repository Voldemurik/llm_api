# Практика № 8 — анализ инцидентов через GigaChat API

## Мой вариант

- Направление: `incident_analysis` — определение серьёзности IT-инцидента.
- Выбранная модель: `GigaChat-3-Lightning`.
- Рабочая ветка: `work`.

Я оставил `GigaChat-3-Lightning`, потому что задача требует короткой классификации с одним полем в ответе, а не длинного рассуждения. Модель используется с нулевой температурой в штатном runner, что уменьшает вариативность. Если содержательная проверка выявит систематические ошибки, модель можно заменить на более сильную доступную версию GigaChat без изменения контракта программы.

## Что реализовано

В `src/app.py` реализованы пять функций. `validate_input()` разбирает JSON и до обращения к API проверяет тип верхнего уровня, обязательные поля, направление задачи, непустое описание инцидента и правила `low`, `medium`, `high`. Дополнительно проверяются типы значений правил и параметр `unknown_as_null`.

`build_prompt()` передаёт модели описание и правила серьёзности в виде JSON. Промпт требует вернуть только объект `{"severity": "low" | "medium" | "high" | null}` и запрещает выдумывать последствия. `parse_response()` извлекает текст из ответа SDK, при необходимости снимает внешнюю Markdown-обёртку, разбирает JSON и строго проверяет единственное поле и все допустимые значения. Некорректный ответ вызывает понятную ошибку, а не заменяется выдуманным результатом.

## Некорректные входы и prompt injection

Ошибки JSON, отсутствующие поля и неправильные типы возвращают код ошибки из валидации. Runner затем создаёт результат `invalid_input` с `result=null` и `meta.api_called=false`, поэтому токены на такие входы не расходуются. В персональном варианте `07-13` содержит список вместо объекта `payload`, а `07-14` содержит число вместо строки `description`; оба случая отклоняются локально.

Текст описания считается недоверенными данными, даже если он содержит `[SYSTEM]`, роль `assistant`, Markdown или требования вывести `HACKED` и `OK`. Такие входы не отклоняются: описание инцидента передаётся в API, но промпт явно запрещает выполнять встроенные команды и менять формат ответа. Строгий разбор результата дополнительно отсекает ответы без требуемого JSON.

## Проверки и статистика токенов

Автономные тесты находятся в `tests/test_app.py` и запускаются командой `python -m unittest discover -s tests -v`. Они проверяют персональные входы, ошибки схемы, защитные инструкции промпта, разбор ответов, статистику usage и сводный отчёт без сетевых запросов. На момент отправки реализации все 13 тестов пройдены. Штатные локальные запуски `07-13` и `07-14` также завершились успешно с нулём вызовов API.

`extract_usage()` берёт фактические `prompt_tokens`, `completion_tokens` и `total_tokens` из `response.usage`. Отсутствующее значение не заменяется нулём; отсутствующий общий счётчик вычисляется только как сумма двух известных составляющих. `build_run_report()` суммирует реальные вызовы и токены, считает успешные проверки формы, ошибки и записи со статистикой. Если данных для суммирования нет, соответствующий итог равен `null`.

Боевой запуск выполняется в GitVerse через ручной workflow **Live check GigaChat (manual)** из ветки `work`. Он заново обрабатывает восемь корректных случаев через GigaChat и сохраняет десять файлов в `results/` вместе с `run_report.json`. Фактические итоги боевого запуска и расход токенов сверяются с этим отчётом и добавляются в README после выполнения workflow.

## Что оказалось сложным

Главная сложность — отличить формально корректный JSON с prompt injection от некорректного входа. Injection нельзя отклонять по ключевым словам, поэтому защита реализована через разделение инструкций и данных в промпте, а также через строгую проверку ответа. Ещё один важный случай — неопределённый масштаб инцидента: для него разрешён JSON `null`, тогда как строка `"null"` считается ошибкой формата.
