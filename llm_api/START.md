# Практика № 8. GigaChat API: от входного JSON до отчёта

В этой работе вы создадите небольшую программу, которая принимает данные, проверяет их, обращается к GigaChat и возвращает структурированный JSON. Дополнительно программа должна корректно обрабатывать попытки prompt injection и считать расход токенов.

**С чего начать:** выполните шаги ниже по порядку. Программировать до получения `TASK.md` не нужно.

## Шаг 1. Получите своё задание

1. Откройте репозиторий GitVerse, созданный из шаблона практики.
2. Создайте **новую ветку от `master`**, например `student/ivanov`. В `master` работать не нужно.
3. Сделайте первый push в новую ветку (если создавали её локально). GitVerse запустит workflow **Assign personal task**.
4. Откройте раздел CI/CD и дождитесь завершения workflow.
5. Перейдите в свою ветку и проверьте, что появились:
   - `TASK.md` — ваше направление и список десяти случаев;
   - `assignment.json` — технические сведения о варианте;
   - `cases/*.json` — десять входных файлов.

**Если задания нет:** сначала проверьте, что смотрите свою ветку, а не `master`, затем проверьте журнал **Assign personal task**. Не создавайте `TASK.md` вручную и не меняйте `assignment.json`.

## Шаг 2. Разберитесь, что нужно написать

Прочитайте **`TASK.md`**, затем **`TASK_CONTRACTS.md`** — там описаны поля результата для вашего направления.

Откройте `src/app.py`. Вам нужно самостоятельно реализовать **пять функций**:

| Функция | Что должна делать |
|---|---|
| `validate_input(raw)` | Прочитать входной JSON, проверить обязательные поля и типы. Вернуть данные или код ошибки. |
| `build_prompt(data)` | Составить запрос к модели, явно указать формат JSON-ответа и отделить инструкции от данных. |
| `parse_response(response)` | Извлечь ответ модели и преобразовать его в JSON-объект нужной формы. |
| `extract_usage(response)` | Получить из ответа API `prompt_tokens`, `completion_tokens`, `total_tokens`. |
| `build_run_report(context, case_records)` | Составить итоговый отчёт с числом запросов, успешных случаев и суммой токенов. |

**Важное различие:** `cases/` — это входные данные, `results/` — ответы, которые создаёт запуск. Не записывайте готовые ответы в программу.

## Шаг 3. Учтите особенности десяти случаев

Вам попадутся три обычных случая, два сложных, два некорректных входа, два случая с prompt injection и один пограничный.

- **Некорректный вход:** программа должна вернуть ошибку проверки *до обращения к API*. Таких случаев два.
- **Prompt injection:** входной JSON формально корректен, но внутри текста кто-то пытается дать модели новые команды. Такие инструкции нельзя выполнять; запрос к API при этом нужен.
- **Пограничный случай:** допустимы неопределённость и `null`, если этого требует контракт.

Поэтому в полном запуске ожидается **8 реальных запросов** и **2 отклонённых входа**.

## Шаг 4. Выберите модель и попробуйте локально

В `model_config.json` есть поле `model`. По умолчанию указана `GigaChat-3-Lightning`. Вы можете выбрать другую доступную вам модель GigaChat.

Установите Python 3.11 и зависимости:

```bash
python -m pip install -r requirements.txt
```

### Где взять доступ к GigaChat и что такое Secrets в GitVerse

Для обращения к GigaChat нужны учётные данные. **Не вставляйте их в `src/app.py`, `README.md`, `TASK.md`, `model_config.json` или коммиты**: даже удалённый из файла ключ может остаться в истории Git.

В workflow `.gitverse/workflows/check.yaml` уже используется секрет с точным именем `GIGACHAT_CREDENTIALS`:

```yaml
env:
  GIGACHAT_CREDENTIALS: ${{ secrets.GIGACHAT_CREDENTIALS }}
```

**Для боевого запуска через GitVerse:**

1. Если преподаватель настроил общий секрет для репозитория или организации, ничего создавать и копировать не нужно: при наличии доступа workflow получит его автоматически.
2. Если преподаватель выдал вам **собственные** учётные данные и поручил добавить секрет, откройте **настройки репозитория → Secrets / Секреты (CI/CD)** (названия пунктов могут отличаться). При наличии прав создайте секрет с именем `GIGACHAT_CREDENTIALS` и вставьте значение туда, а не в исходный код.
3. Запускайте **Live check GigaChat (manual)** из своей ветки. GitVerse передаст секрет процессу как переменную окружения. Значение не нужно печатать в логах.
4. Если секрет недоступен или API возвращает ошибку авторизации, проверьте права workflow и настройку секрета; при централизованной выдаче обратитесь к преподавателю. **Не пытайтесь исправить ошибку, записав ключ в Python-файл.**

**Для локального запуска:** секрет из GitVerse **не переносится на ваш компьютер**. Нужны отдельные доступные вам учётные данные, переданные в переменной окружения, например в PowerShell:

```powershell
$env:GIGACHAT_CREDENTIALS = "<ваши_учётные_данные>"
```

Не сохраняйте команду с настоящим секретом в репозитории, скриншотах и отчётах. Если локального доступа нет, согласуйте с преподавателем способ тестирования.


Для пробного запуска одного случая:

```bash
python .practice/scripts/live_run.py --local --only 01-01
```

Замените `01-01` на **ID из вашего `TASK.md`**. Команда обращается к настоящему API и расходует токены. Исправляйте код и повторяйте локальные пробы по необходимости.

## Шаг 5. Подготовьте решение

Закоммитьте в **свою ветку** исходный код и выбранную модель. Убедитесь, что все пять функций реализованы.

Не изменяйте `cases/`, `assignment.json`, `.practice/` и `.gitverse/workflows/`. Не добавляйте API-ключи.

## Шаг 6. Запустите боевую проверку

1. В GitVerse откройте **CI/CD → Live check GigaChat (manual)**.
2. Выберите **свою рабочую ветку** и запустите workflow вручную.
3. CI выполнит вашу программу на всех десяти случаях. Для восьми корректных входов он **заново вызовет GigaChat**; кэш локальных результатов не используется.
4. CI проверит форму JSON, статистику токенов и отчёт. Результаты будут сохранены в `results/*.json` и `run_report.json` вашей ветки.
5. Откройте лог workflow. Если есть `[FAIL]` или `[REPORT FAIL]`, исправьте код и повторите запуск вручную.

**Не пугайтесь красного статуса:** результаты частично успешного запуска тоже сохраняются, чтобы было видно, что именно сломалось.

## Шаг 7. Сдайте работу

Убедитесь, что в ветке есть:
- ваш `src/app.py`;
- выбранная модель в `model_config.json`;
- десять результатов в `results/`;
- итоговый `run_report.json`.

Заполните **`README.md` своими словами**: укажите направление, выбранную модель, как работает программа, как обрабатываются ошибки и инъекции, сколько токенов ушло на боевой запуск и какие сложности встретились. Сверьте числа с `run_report.json`. Затем создайте **Pull Request из своей ветки в `master`**. Не сливайте PR самостоятельно, если преподаватель не разрешил.

## Где искать помощь

- `TASK.md` — **что именно решать**;
- `TASK_CONTRACTS.md` — **какие поля должны быть в ответе**;
- `src/app.py` — **что писать**;
- `.practice/scripts/live_run.py` — **как запускается решение** (изменять не нужно);
- логи **Live check GigaChat** — **почему проверка не прошла**.

**Важно:** автоматическая выдача задания не тратит токены. Локальные пробы и ручная боевая проверка — тратят. Ключ GigaChat хранится только в переменной окружения или секрете GitVerse.

## Почему есть папка `.practice/`?

Это **служебная часть практики**: банк заданий, индекс `manifest.json`, генератор, runner и тесты. Вам не нужно её редактировать или читать, чтобы выполнить задание. В корне находятся `START.md`, ваш `README.md`, `model_config.json` и файлы варианта; код пишется в `src/app.py`.

## Проверка README перед боевым запуском

`README.md` — часть вашей работы. **До запуска GigaChat** CI проверяет, что вы убрали подсказки `TODO`, указали выбранную модель (точно как в `model_config.json`) и кратко описали решение, некорректные входы, prompt injection, запуск и учёт токенов. Заголовки можно выбирать самостоятельно.

**Не нужно заранее знать число токенов!** На первом запуске опишите, как ваш код собирает статистику. После успешного запуска дополните README фактическими результатами из `run_report.json`.

Проверить README локально без расходов на API:

```bash
python .practice/scripts/check_readme.py
```

Если проверка не прошла, CI завершится до обращения к GigaChat, а в журнале появится `[README FAIL]` с причинами. Эта проверка оценивает только минимальную заполненность, а не качество объяснения.
